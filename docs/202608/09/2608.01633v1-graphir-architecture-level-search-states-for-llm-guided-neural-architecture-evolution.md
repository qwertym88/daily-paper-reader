## 摘要
大语言模型（LLMs）使得神经架构搜索（NAS）能够直接在可执行的神经网络程序上进行。然而，代码级灵活性并未提供有效变异所需的架构状态：LLMs必须从实现细节中推断张量依赖、可编辑组件和兼容性约束。为解决这种表示不匹配问题，我们提出GraphIR，一种架构感知的中间表示，它以变异对齐的候选状态补充可执行程序。GraphIR通过三个互补视图组织每个候选：描述张量流的计算骨架、暴露可编辑模块和操作的变异表面，以及捕获接口契约、传播形状和下游依赖的有效性边界。为评估我们的方法，我们构建了NAS-Dependency，一个包含120个问题、涵盖六个互补依赖推理维度的基准测试。诊断显示，GraphIR在识别精确生产者出现、追踪依赖传播以及诊断接口和失败风险方面特别有效。在包括CLRS在内的六个下游基准上，GraphIR在集成到OpenEvolve时实现了最佳的整体搜索性能，同时保持相当的模型规模和有利的端到端NAS效率。这些结果表明，面向变异的架构状态为可执行神经程序与LLM引导的架构演化之间提供了有效接口。

## Abstract
Large language models (LLMs) enable neural architecture search (NAS) directly over executable neural network programs. However, code-level flexibility does not provide the architecture state needed for effective mutation: LLMs must infer tensor dependencies, editable components, and compatibility constraints from implementation details. To address this representation mismatch, we propose GraphIR, an architecture-aware intermediate representation that supplements executable programs with a mutation-aligned candidate state. GraphIR organizes each candidate through three complementary views: a computation skeleton describing tensor flow, a mutation surface exposing editable modules and operations, and a validity envelope capturing interface contracts, propagated shapes, and downstream dependencies. To evaluate our method, we construct NAS-Dependency, a 120-question benchmark covering six complementary dependency-reasoning dimensions. The diagnostic shows that GraphIR is particularly effective at identifying exact producer occurrences, tracing dependency propagation, and diagnosing interface and failure risks. Across six downstream benchmarks including CLRS, GraphIR achieves the best overall search performance while maintaining comparable model size and favorable end-to-end NAS efficiency when integrated into OpenEvolve. These results show that a mutation-oriented architecture state provides an effective interface between executable neural programs and LLM-guided architecture evolution.

## 1. 论文的核心问题与整体含义

- **研究背景**：神经架构设计本质上是“表示问题”（representation problem）。近年来的 LLM-guided NAS 允许大语言模型直接在**可执行的神经网络程序**上进行架构搜索与变异，这种“代码级”搜索空间比传统 NAS（基于固定 grammar 的 cell graph、操作集等）更加开放灵活。
- **核心矛盾（表示不匹配）**：可执行代码虽提供了开放的变异载体，但**架构级状态是隐式的**。LLM 必须从实现细节中自行推断：哪些组件是有效的变异目标、张量维度如何耦合、修改某个表示后哪些下游模块会受影响、哪些输入输出契约必须保持。这导致两种典型失败：
  - 语法合法但架构不一致的候选（如张量形状不兼容、破坏评估器接口）；
  - 可执行但无效的变异（只改实现细节，没有产生有意义的架构变化）。
- **核心研究问题**：当 LLM 对可执行神经架构进行变异时，应当观察到什么样的候选状态（candidate state）？
- **论文主张**：变异对齐（mutation-aligned）的架构状态需要三个互补视图——**计算骨架**（张量流）、**变异表面**（可编辑组件）、**有效性边界**（接口契约与依赖约束）。据此提出 **GraphIR**，作为可执行程序与 LLM 引导架构演化之间的桥梁。

## 2. 方法论：核心思想与关键技术细节

### 2.1 总体框架

- GraphIR 不取代源代码，而是**保留源代码作为可执行、可编辑的搜索对象**，同时补充显式的架构级候选状态。
- 变异过程形式化：
  - 常规：\(P_{t+1} \sim \pi_{LLM}(\cdot \mid P(P^{par}_t, H_t))\)
  - 加入 GraphIR 后：\(P_{t+1} \sim \pi_{LLM}(\cdot \mid P(P^{par}_t, G_t, H_t))\)，其中 \(G_t = \text{GraphIR}(P^{par}_t)\)
- 每个生成的子代程序都会重新构建 GraphIR，使新引入的模块、依赖关系在后续迭代中立即可见。

### 2.2 GraphIR 状态定义

- 状态形式化表示为：\(G(P) = (I, O, M, T, F, E)\)
  - **I / O**：输入/输出接口契约
  - **M**：架构模块集合
  - **T**：架构相关张量操作
  - **F**：确定性结构事实
  - **E**：生产者—消费者依赖关系
- 三个互补视图：
  - **计算骨架**（M, T, E）：描述主要张量变换及其顺序；
  - **变异表面**（M, T, F）：暴露可作为变异目标的架构组件与结构属性；
  - **有效性边界**（I, O, E）：记录变异后必须保持兼容的外部接口与内部依赖。

### 2.3 构建流程（Algorithm 1）

1. 选择标记的演化区域（或整个程序）；
2. 基于程序 profile 初始化默认契约 I、O（如图结构 vs. 通用 PyTorch 契约）；
3. 通过 Python AST 静态分析提取 M、T、静态事实 Fs 和静态依赖 D；
4. 实例化候选程序并合成示例输入（无法推断宽度时用预设特征宽度）；
5. 通过 **PyTorch FX 符号追踪** 恢复计算图，做形状传播，得到 FX 依赖 Efx 与观测契约；
6. 用观测到的输入/输出形状修正 I、O；
7. 从追踪图中生成执行可落地的事实 Fe；
8. 优先使用 Efx，不可用时回退到静态依赖 D；
9. 合并去重 Fs 与 Fe 得到 F；
10. 按固定字段顺序渲染 G(P) = (I, O, M, T, F, E)。

### 2.4 关键设计细节

- **模块识别**：基于固定神经模块词表（线性、卷积、归一化、循环、注意力、正则化、池化等）；
- **操作识别**：覆盖激活、形状变换、拼接、堆叠、归约、掩码、矩阵乘法、张量缩并等，并记录二元加法、循环、条件语句；
- **结构事实**：通过固定“触发器→标签”规则生成（非 LLM 摘要），如卷积→局部混合事实、加法→加性融合事实；同时合并执行层事实并去重；
- **依赖关系**：优先用 FX 图的生产者—消费者边；不可执行时使用保守的赋值级静态依赖，排除模块构造器依赖和非张量属性初始化以减少假边；
- **紧凑渲染**：过滤不传达架构结构的节点，对渲染实体数量设上限，保持上下文精简。

## 7. 局限性与未来工作

- **静态分析的边界**：GraphIR 依赖 Python AST 与 PyTorch FX 符号追踪，对包含动态控制流、非 FX 可追踪算子或重度依赖外部库的模型支持有限；对于这类程序，GraphIR 只能退回到静态依赖，精度会下降。
- **架构有效性的概率性保证**：GraphIR 虽然显式暴露了接口契约与依赖约束，但并不能严格证明变异后的候选一定满足可执行性与架构一致性，只能提高 LLM 生成有效候选的概率。
- **单一 LLM 验证**：所有实验均基于 Qwen3-Plus，未测试不同规模或不同家族的大语言模型，因此无法判断 GraphIR 的收益是否与底层 LLM 的代码推理能力存在强耦合。
- **搜索空间依赖**：GraphIR 本身不定义新的搜索算子，其收益受限于 OpenEvolve 的变异机制；对于 OpenEvolve 难以探索的架构变化，GraphIR 也无法直接创造新的搜索路径。
- **模块词表固定**：GraphIR 的模块识别依赖预定义的神经模块词表，对于尚未收录的全新架构原语（如新的自定义算子）可能无法准确识别，从而削弱变异表面的覆盖度。

## 8. 整体评价与思考

- **核心贡献**：论文指出了一个重要但常被忽视的问题——在代码级 LLM-guided NAS 中，架构状态是隐式的，而 LLM 需要显式的、变异对齐的表示才能有效推理。GraphIR 作为一个轻量级中间表示，通过计算骨架、变异表面和有效性边界三个互补视图，架起了可执行程序与 LLM 架构演化之间的桥梁。
- **方法价值**：GraphIR 不是一个新的搜索算法，而是一种表示层的增强，因此可以与不同的 LLM、变异策略和搜索协议正交组合，具有较强的通用性和迁移潜力。
- **实验设计的亮点**：新增的 NAS-Dependency 诊断基准以真实演化轨迹为基础，将“表示质量”从下游搜索性能中分离出来，直接衡量不同表示对依赖推理的帮助，这是一个值得借鉴的评估思路。
- **可改进之处**：统计严谨性有待加强（如种子数不对称、部分结果只报告单次最优运行），跨 LLM 的泛化验证缺失，CLRS 中部分基线直接引用原论文结果导致比较协议不完全一致。未来若能补充多模型实验、更严格的统计检验以及与更多基线在统一协议下的对比，结论会更有说服力。
- **总体判断**：GraphIR 在多个基准上一致地提升了 LLM 引导架构搜索的性能与效率，且诊断基准进一步表明其收益来源于更好的依赖推理能力而非偶然因素。尽管存在局限，该工作为表示工程在自动化模型设计中的应用提供了一个清晰、有效且易于复用的范本，值得后续研究深入探索。

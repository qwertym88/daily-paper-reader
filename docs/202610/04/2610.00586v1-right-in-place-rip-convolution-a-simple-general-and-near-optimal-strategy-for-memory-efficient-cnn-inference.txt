# Right In-Place (RiP) Convolution: A Simple, General, and Near-Optimal Strategy for Memory-Efficient CNN Inference

## Abstract 

Activation memory, not compute, limits CNN inference on constrained hardware such as microcontrollers. Direct in-place convolution removes the dual-buffer cost, but the memory-optimal formulation of Gural and Murmann [9] assumes valid padding, unit stride, unit dilation, and odd square kernels, and needs a non-sequential traversal cost-ing 2× inference time in transposes. We identify two regimes in which their published closed form does not hold: (1) an under-allocation of exactly (k − 1) Cin mod ( Cout −

Cin ) scalars, active on every convolutional layer of their own deployed network and manifesting as a silent corrup-tion of still-live input; (2) an unbounded overestimate, up to 2,432 ×, once the critical leg leaves the output grid. We correct both and generalize to arbitrary stride, dila-tion, padding, and rectangular kernels. We then propose Right In-Place (RiP) convolution, a bit-identical opera-tion in which every layer reads its input right-aligned in a shared workspace and writes its output left-aligned from index zero. The debt is piecewise affine in the output pixel index, so evaluating its breakpoints in O(1) yields the min-imum safe gap without enumerating the output grid, with row-major access preserved. Across 10 ,000 random lay-ers RiP produced no corruption, and across 84 convolu-tional layers from 25 architectures it matches the herring-bone workspace exactly on 58 and within 5% on 81, using 24.8% less memory than dual buffering on average. Written into TinyEngine’s [19] kernels and deployed to a Raspberry Pi Pico 1 and Pico 2, it cuts peak activation memory across eleven MCUNet models by 12.5 to 33.3% at unchanged cy-cle counts and bit-identical outputs, raising the number of models that fit the Pico 1’s 256 KB SRAM from six to nine. 

## 1. Introduction 

Inference is moving from the cloud to the edge, where run-ning locally keeps user data on the device, tolerates inter-mittent connectivity, and fits a single-Joule power envelope. The memory hierarchy is what constrains it: a modern GPU has tens of gigabytes of DRAM, a mid-range microcon-troller (MCU) such as the RP2040 has 256 KB 1 of SRAM, and the low-end 8-bit class still shipped by the billion pro-vides 2–16 KB. That makes deployment a memory problem before it is a compute problem, and one question decides whether a net-work runs well: does the working set fit in the fast memory tier, or must it spill to a slower and more energy-expensive one [14]? Weights are by now well served, with pruning, quantization, and bit-packing reaching compression above 

50 × [3]. Activations are not. They must be materialized during inference, and for the early layers of a typical CNN, the input feature map alone can exceed the budget. Mi-crocontrollers make this hardest and motivate our analysis, but nothing in it is specific to them: the same accounting governs any device whose working set competes for a fast memory tier. Direct in-place convolution, overwriting stale input acti-vations with new outputs as computation proceeds, needs no auxiliary buffer, no cross-layer scheduling, and no hardware modification. It works because convolution sits between two extremes. In-place execution is routine for an element-wise operator such as ReLU, where each output depends on one input, and impossible for a dense layer y = W x , where nothing goes stale until the whole output exists. Specifi-cally, a convolution output depends on a bounded neighbor-hood of khkwCin inputs, so what is needed is not a second buffer but a gap : a bounded region of slack memory be-tween the write frontier and the next live input. Determining that gap is the problem this paper solves. Gural and Murmann [9] prove that a herringbone traver-sal minimizes activation memory for direct convolution, fit-ting an MNIST classifier into 2 KB of SRAM. Two gaps remain. Their analysis assumes valid padding, unit stride,

Modern CNNs violate every one of these assumptions: strided downsampling [22], dilated convolutions [6], non-square kernels [28], and same-padding are staples of ResNet [12], MobileNet [15], Ef-ficientNet [29], and MCUNet [19]. Also, the geomet-ric lemma at its heart does not generalize to anisotropic receptive fields. Moreover, optimality demands a non-sequential traversal, forcing an in-place transpose at every row–column switch and a final inverse permutation, which the authors report costs 2× inference time. 

Contributions. We identify two regimes in which the published closed form fails, one under-allocating and one overestimating without bounds, and correct both. We gen-eralize the analysis to arbitrary stride, dilation, padding, rectangular kernels, and uneven output grids. We then pro-pose Right In-Place (RiP) convolution, a row-major layout whose minimum safe gap is obtained by breakpoint evalu-ation, and validate it on 10 ,000 synthetic layers, 84 layers from 25 architectures, and nine and eleven MCUNet models deployed to a Raspberry Pi Pico 1 and Pico 2 respectively. 

## 2. Related Work 

Work on activation memory for kilobyte-scale devices di-vides along the axis of memory reuse that each method ex-ploits. Tab. 1 places our contribution (a fine-grained spatial 

in-place scheme for general channel-mixing convolutions) against the rest. 

Spatial in-place convolution. Gural & Murmann [9] first showed that direct convolution can overwrite stale input ac-tivations with new outputs, and proved that a herringbone 

traversal of the output grid, alternating rows and columns so that edge pixels are reclaimed as early as possible, achieves the minimum activation memory under valid padding, unit stride, unit dilation, and odd square kernels. The result is memory-optimal but costs a non-sequential output order, an in-place transpose at every row-to-column switch, and a fi-nal inverse permutation; their Arduino case study reports 

2× inference overhead ( 819 s against 396 s ). Their concur-rently introduced Replace strategy runs row-major at naive speed, but is only analyzed for the same restricted setting and fragments freed memory at row ends. Neither has been extended to arbitrary stride, dilation, padding, or rectangu-lar kernels, and few subsequent methods have revisited the layout problem itself. Zhang et al. [30] reorder loops for “zero-memory-overhead” direct convolution, but measure overhead beyond the storage of the input and output activa-tions, so a full output buffer is still allocated. RiP extends the Gural & Murmann analysis to arbitrary parameters and removes the transpose overhead, using a fragmentation-free single-gap layout with an O(1) closed-form gap. The closest confusable work is buffer replacement. Sakr et al. [25] extend CMSIS-NN with a single arena sized to the largest pair of adjacent layer activations so that every layer draws its input and output from the same reused space, cut-ting whole-network activation memory by roughly 27 .2% .However, within a layer, the convolution is still dual-buffered; the granularity is the whole tensor, and the de-cision is made between layers so a layer’s own input and output coexist while it runs. RiP overlaps those two in one buffer sized by the worst instant, and the two compose: our per-layer bound sets the size of the very tensors such an arena must pack. 

Other axes. Channel in-place exploits the fact that depth-wise convolutions do not mix channels, so the input ac-tivation of channel γ may be overwritten by the output of channel γ+1 . TinyEngine [19, 20] measures a 1.6×

peak reduction on depthwise layers and TinyAD [27] for-malizes the same reschedule with a transit buffer. Nei-ther can apply to the 3×3 and pointwise 1×1 convolutions that dominate modern activation memory, which is exactly the case RiP targets. Cross-layer methods attack the peak from outside the layer: MCUNetV2 [21] computes a spa-tial patch across several layers before advancing, cutting MobileNetV2’s peak by up to 8× at the cost of recomputa-tion, and fused depthwise tiling [26] and line-buffer pipelin-ing [17] reach the same end by other means. All still pay the full HpWpCin + Hout Wout Cout inside any single bottle-neck layer; RiP attacks that residual, and the patch itself can be executed in our layout. In silicon, RAMAN [18] overlays the input and output activation buffers on one on-chip region for up to 50% storage reduction — the coarse, whole-buffer analogue of our idea, tied to a specific dataflow and requir-ing custom hardware. 

Memory planning. A parallel line treats activation memory as tensor-lifetime allocation. TFLite Micro packs tensors into a fixed arena by first fit [8]; iterative graph optimization [31] cuts the peak by up to 26.4% against it, and MoteNN [7] by up to 80% against prior coarse-grained schedulers. These answer “given a set of tensor lifetimes, how tightly can we pack them?” RiP answers the lower-level question of what the smallest workspace is un-der which a single convolution can execute at all, so a tighter per-layer bound shrinks the tensors any planner must pack. Weight quantization [11, 16, 24], pruning [10, 13, 23], ar-chitecture search [4, 5], bit-packing [3], and fused-layer ac-celerators [2] all reduce total model footprint or cross-layer traffic without altering the intra-layer activation peak, and are complementary throughout.

## 4. Right In-Place Convolution 

Sec. 3 corrected the herringbone peak debt but kept its non-sequential traversal, and with it the transpose over-head. This section presents Right In-Place (RiP) convolu-tion: a row-major 3 (Fig. 2b) single-gap layout whose mini-mum safe gap follows from a piecewise affine debt function. The gap is solved in O(1) by evaluating that function at nine breakpoints, no transpose and no reorder are required, and the derivation places no restriction on stride, dilation, padding, or kernel shape.

4.3. Execution and Re-Alignment 

Given a workspace of ∆∗ + HpWpCin scalars with the padded input right-aligned at offset ∆∗, the layer visits 

(r, c ) in row-major order and writes each output pixel to 

(rW out +c)Cout . How that pixel is computed (nested loops, im2col plus GEMV, or a fused kernel) is unconstrained. The one prerequisite is that the input is not needed again, which holds for any layer whose input is not consumed by a skip connection off the same tensor. Both tap-read orders appear in this paper, and which one is used is dictated by what is being compared. The deploy-ment of Sec. 5.4 relies on TinyEngine’s default behavior of gathering the receptive field into a temporary buffer [19]. Because this buffer is an engine-level constant required identically by the dual-buffer baseline, it sits outside the activation arena, setting σ = 0 so the RiP gap carries no production-order headroom penalty. On the other hand, the layer-level comparison of Sec. 5.3 uses σ = Cout , be-cause the herringbone accounting of [9] assumes taps are read from the workspace and matching it is what makes that comparison like for like. RiP is therefore measured against herringbone under herringbone’s own execution order, and deployed under the cheaper one. In RiP, output emerges left-aligned while the next layer expects its input right-aligned, so the two must reconcile. Under dynamic allocation this is free: the next layer’s in-put pointer is set ∆∗ scalars past the buffer origin and no data moves. A device working from a single predetermined workspace has no pointer to move, and the obvious rem-edy is one O(HpWpCin ) memmove (right shift) per layer against the O(Hout Wout khkwCin Cout ) convolution. In practice it does not come to that, because what a layer needs is slack memory to the left of its input, and the gap may sit at either end of that layer’s allocation. Therefore, a move is forced only when the layer’s input already occupies its workspace from the left. Consequently, we solve the placement once for the whole network, offline, with a mixed-integer linear pro-gram (MILP) that replaces the greedy first-fit allocator of TinyEngine’s code generator. The re-alignment cost we measure is zero, and the bias in the objective is the reason that is a result. The allocator is not itself a source of saving. On naive dual buffering and on TinyEngine’s own schedule, the pro-gram reaches the same peak as first-fit, so the reductions in Sec. 5.4 are attributable to the layout alone. Under RiP it is load-bearing for a different reason. A layer’s freed gap is useful only if a later tensor can be placed in it, and first-fit commits offsets in schedule order without a lookahead; on MCUNet-in2 and in3 (Fig. 1), whose branch connec-tions keep two tensors alive across the shrunken layer, it strands the reclaimed space between live tensors and returns no peak reduction at all despite the smaller buffers. Solv-ing placement globally is what converts a per-layer bound into a network-level saving. Either way the layout resolves the “inconveniently laid-out stale memory” obstacle that led Gural and Murmann to abandon the row-major setting [9, §3.4.1], without herringbone’s 2× transpose overhead. Ten-sor packing is NP-hard, but the instances are small: across 33 convolutional keras.applications models the full offline step (parse, model build, and solve) takes under 150 s; Sec. I details this experiment. 6Padding need not be materialized. Eq. (4) stores the padded input in full, as TensorFlow does [1], although the 

(HpWp − Hin Win )Cin border cells all hold the same pad value: for a same-padded 3×3 convolution on a 32 ×32 fea-ture map they are ∼11% of the input footprint. Storing only the Hin Win Cin real scalars is possible, and the supplemen-tary material re-derives the bound under this dense layout, at O(khkw) rather than O(1) because the debt now kinks wherever a tap crosses the padding boundary. The result belongs here because its sign inverts: the gap grows, since a smaller input footprint pre-allocates less slack for the output to consume, while the workspace shrinks. What has to fit in SRAM is the workspace, and Eq. (42) makes the trade pre-cise. A practitioner comparing the two layouts by gap will therefore reject the one that wins. The saving costs only in-dex arithmetic; Sec. F.4 gives the one regime in which the bound is safe but not tight. 

## 5. Results 

5.1. Experiment Setup 

We evaluate three claims separately: that the closed forms are safe and tight (Sec. 5.2), that they are competitive on the layers from which real networks are built (Sec. 5.3), and that the savings survive deployment (Sec. 5.4). The first is analytic and is checked against a simulator that never eval-uates a closed form; the other two are measured on device. 

5.2. Synthetic Layers 

A traversal is correct exactly when no output write lands on an input scalar that an unwritten output still needs; the dot product itself is unchanged, so liveness is the only prop-erty at issue. We generated 10,000 layers across 20 param-eter categories, spanning the ranges real networks occupy together with small-grid, thin-axis, and degenerate regimes that are rare or absent in practice, and ran each through the corruption simulator under five execution configurations. Of the 10,000, 22.6% fall inside the restrictions of [9]; the rest are reachable only through the generalization in Theo-rem 11. No configuration produced an unsafe gap. The RiP and generalized herringbone bounds are not merely safe but tight, equal to the simulator’s minimum on every one of the 10,000 layers. The dense bound is tight on 99 .1% when taps are read directly from the workspace. The exception is layers in which some real input is never read by any out-put and is dead before the layer starts, so that the count of dead scalars no longer determines which addresses are dead; Sec. F.4 gives the mechanism and the two conditions under which it costs anything. The bound remains safe there, overshooting by 91 .85 scalars on average. Gather-ing the receptive field into a temporary buffer first removes the exception and the bound is tight on all 10,000. 

5.3. Real Architectures 

We then compared the naive dual-buffer workspace, the generalized herringbone workspace and the RiP workspace analytically across 84 convolutional layers drawn from 25 architectures spanning classification, detection and speech; Tab. 6 lists them by family. Layers were selected to prior-itize peak activation memory rather than to sample archi-tectures uniformly: for each network, we take the layers whose combined input and output footprint is largest, since it is those layers that determine whether the network fits a given device at all. Each traversal is first confirmed against the corruption simulator, which executes it in an allocation-tracked buffer; the generalized herringbone form matches on all 84. We also run the 48 layers that fit on the Pico 2 and show that the right-shift is close to free: every one costs within 1% 

of the dual-buffer kernel, five run marginally faster, and the right-shift is a median 0.05% of layer conv runtime, worst 

0.83% . Forty-three of the 84 layers fall outside the parame-ter range of [9] (strided, dilated, padded, or rectangular), so the generalization is not a formality but the condition under which the comparison exists at all. RiP matches the herringbone workspace exactly on 58 of the 84 layers and to within 5% on 81, at a mean reduc-tion of 24.8% against naive allocation (median 25.0%, best 50.0%). Sequential access therefore costs almost nothing in workspace terms, and where it does, the cost is structural rather than diffuse. On every layer whose output tensor is no larger than its padded input (25 of the 84) RiP and her-ringbone agree exactly, without exception. When the out-put is larger, the excess cannot be absorbed into the space the input vacates and must be carried in the gap, where a row-major frontier accumulates debt across a full row be-fore releasing any of it. All three layers exceeding 5% are of this kind: two channel-doubling layers of pruned VGG-16 on small grids, and the worst at 17.0%, an Inception-v3 

7 × 1 branch whose kernel is maximally anisotropic. Since both the row and column bounds are computable in O(1) ,a practitioner meeting such a layer can evaluate them and transpose the input and kernels to process in column order instead, which in this case matches herringbone gap exactly.

We deploy all eleven open-source MCUNet models [19] to two boards, a Raspberry Pi Pico 2 (RP2350, 520 KB SRAM) and a Raspberry Pi Pico 1 (RP2040, 256 KB SRAM), at each model’s native resolution with int8 weights and activations. The baseline is TinyEngine’s own deploy-ment with in-place depthwise convolution enabled, so the workspace reduction reported here is measured against the state of the art rather than against naive dual buffering. ## 6. Conclusion 

We corrected two limitations in the published herringbone closed form: a silent under-allocation active on every con-volutional layer of the authors’ deployed network, and an unbounded overestimate outside the output grid. We also generalized the analysis to arbitrary stride, dilation, padding, and rectangular kernels. Right In-Place convolu-tion then recovers row-major order at a gap solved by break-point evaluation, removing 12.5 to 33.3% of peak activation memory across eleven deployed models at unchanged cycle count and bit identical output. Because the memory saving costs no time, the choice between the two is not a trade-off. Scope of the optimality claim. Theorem 11 establishes the exact peak debt of the generalized herringbone traver-sal . Whether herringbone remains memory-optimal among all traversals under arbitrary parameters is a separate ques-tion, and the answer is no. Gural & Murmann’s optimality argument [9, Lemma 3.1] rests on a Chebyshev-ball isoperi-metric bound that assumes an isotropic square kernel and does not extend to anisotropic receptive fields. More di-rectly, when sh > k eff  

> h

or the dilation is large enough, some input pixels are stale on arrival: no output ever depends on them. A traversal that discards those before storing the in-put and then runs herringbone uses strictly less memory, so herringbone without such a pruning step cannot be optimal in that regime. We do not pursue the pruned variant here. Theorem 11 is used only as a baseline against which RiP is compared, and the figures in Tab. 6 are herringbone peak debts rather than traversal-optimal minima.

## G. Validation Protocol 

Every closed form in this paper is checked against a simula-tor that does not know the formula. This appendix describes the simulator, how the 10 ,000 configurations of Sec. 5.2 are composed, and what the check does and does not establish. 

G.1. The Corruption Simulator 

The simulator executes a traversal literally in an allocation-tracked workspace. It holds a scalar-level map of the buffer, marks each input scalar live until the last output pixel that depends on it has been computed, and flags a corruption the moment a write lands on an input tap still marked live. Given a layer configuration it binary-searches the gap: the smallest ∆ that completes the traversal with no flag is the ground truth reported as Truth in Tab. 2. Two properties make this a check rather than a restate-ment. The simulator never evaluates any closed form, so agreement is independent evidence. And it returns the mini-mum rather than a safe value, so it catches over-allocation as well as under-allocation: this is what exposed Limitation 2, where the published form exceeds truth by up to 2,432 ×,and the degenerate leg sequence of Sec. E.3. Each configuration therefore receives one of three ver-dicts per closed form: UNSAFE if the formula falls below truth, which is the only outcome that admits a corruption;  

> TIGHT

if it equals truth; and LOOSE if it exceeds truth by any number of scalars. No sweep in this paper has produced an UNSAFE verdict.

G.3. What the Sweep Does Not Establish 

The sweep establishes that the gaps are safe and, where re-ported, tight. It does not establish that a layer executed in the RiP layout computes the same tensor as one executed conventionally, which is a separate claim and the one a prac-titioner cares about. Liveness bookkeeping and arithmetic are different questions: a gap can be safe while the kernel is wrong, and a kernel can be right while the gap is too small. The sweep only answers the former question, a correctly implemented kernel answers the latter. The end-to-end claim is discharged on device instead, and more strongly than a synthetic check would. Every de-ployed model in Tab. 3 carries an on-device checksum of its output logits, computed after the full network has run under RiP and compared against the same checksum under the baseline schedule. All eleven agree bit for bit. Since RiP changes only where activations are placed and not how they are computed (that is the kernel implementation’s busi-ness), the agreement over eleven networks is the observed and expected behavior. 17 H. ## I. Graph-Level Simulation and MILP Cost 

The eleven deployed models of Tab. 3 are small enough that solver cost is not in question. To see how the MILP behaves on larger model graphs, we stripped TinyEngine’s kernel generators from its TFLite parser, keeping the graph API and layer construction, branch connections, and ten-sor liveness, and ran the allocator alone across 33 mod-els from keras.applications : DenseNet (121, 169, 201), EfficientNet (B0–B7), EfficientNetV2 (B0–B3, S, M, L), ResNet and ResNetV2 (50, 101, 152), MobileNet, Mo-bileNetV2, MobileNetV3 (Small, Large), VGG (16, 19), In-ceptionV3, InceptionResNetV2, and Xception. These are not deployed; the point is to study the cost of the allocator and not execution on the boards. Every layer runs under the dense layout of Sec. F with the receptive field gathered first, so padding is never materialized and σ = 0 . The allo-cator was run on an 8-core (16-thread) Intel processor at 1.80 GHz base (4.50 GHz turbo) with 64 GB of memory, using SCIP through the Pyomo interface. Each model is solved single-threaded, with four models measured concur-rently. We report the median of 10 runs per model and per formulation. 

Scaling. The program size is quadratic in the graph by construction: the pairwise no-overlap constraints put three overlap binaries on each of the n(n−1) /2 tensor pairs, so the dual-buffer formulation has exactly 3n(n−1) /2 bina-ries on all 33 models, and RiP adds 2m for the m in-place candidates. Cost per binary, however, is flat. Regressing on the number of binaries over a 46 × range in graph size (n = 22 to 1,006 ) gives an exponent of 1.05 for model con-struction ( R2 = 0 .99 ) and 0.99 for the branch-and-bound search ( R2 = 0 .97 ): both stages are linear in the size of the program they are given. Against tensor count the exponents are 2.10 and 1.98 , which is that linearity composed with the quadratic encoding rather than a solver that degrades with scale. 

Cost. The largest instance, EfficientNetV2-L, has 1,006 tensors, 1.52M binaries and 2.03M constraints, and takes 132 s. No model in the set exceeds 150 s and the me-dian is 13.0 s. The branch-and-bound search dominates model construction on 30 of the 33 (96.3 s against 34.8 s on EfficientNetV2-L), so the cost is the packing problem rather than the Python that builds it. The problem grows with the graph and not with the tensors: VGG-16 has the 

9th largest activations in the set and the smallest program (729 binaries, 0.16 s), while EfficientNetV2-L, only 5th by activations, has the most nodes and the largest. Against the dual-buffer baseline the RiP formulation compiles between 

0.99 × and 2.36 ×, median 1.53 ×, which is the price of the extra binaries di and ri. All of it is offline and paid once per model. 

The baseline is not greedy. The comparison here is against the same MILP restricted to dual-buffer execution, so both sides solve an NP-hard packing problem and the baseline achieves the optimal packing of never-aliased ten-sors. All operations are dual buffered and a used memory space is made available only once the tensor’s lifetime ends. The reductions are therefore conservative: RiP cuts peak activation memory on all 33, by 20.0% to 49.8% (mean 32.6%), against an allocator that is already optimal within its execution model. 

In-place is not forced. The objective minimizes peak memory plus the right-shift penalty of Sec. 4.3. Operator classes. Every model layer falls in one of two classes. Concatenation, reduction and fully-connected lay-ers need disjoint input and output and are held apart by con-struction, so they are forced to dual buffering regardless of the allocator mode. Convolution, depthwise convolution, pooling, element-wise and scalar add and multiply, upsam-pling, and activations are candidates for in-place placement, and the MILP decides. Treating tensors as candidates for in-place placement rather than being forced to be aliased mat-ters on residual topologies, where an activation’s input may still be live for a downstream skip connection; the liveness constraints make the program fall back to disjoint place-ment in exactly those cases. 19 Upsampling.

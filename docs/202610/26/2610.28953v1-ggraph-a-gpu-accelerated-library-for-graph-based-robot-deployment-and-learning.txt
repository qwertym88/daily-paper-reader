# GGraph: A GPU-Accelerated Library for Graph-Based Robot Deployment and Learning 

Yash Rampuria 1, Rohan Garg 1, Daniele Gammelli 1 and Marco Pavone 11Stanford University, CA 

Abstract — Autonomous mobile robots require spatial repre-sentations that capture geometry and semantics while staying sparse enough for planning in large, unknown environments. Graphs provide a natural representation for this purpose and underpin both classical planning methods and a growing class of reinforcement-learning (RL) policies. However, RL training needs hundreds to thousands of parallel environ-ments, each constructing and updating its own graph. Existing graph libraries are typically designed for either single-robot deployment or fixed graphs, and CPU-based graph construction limits scalable training to only a few dozen environments. We introduce GG RAPH , an open-source GPU-accelerated graph library for both robot deployment and large-scale learning. GG RAPH supports real robots through ROS 2 interfaces and vectorized GPU-based policy training, with built-in support for tasks including 3-D navigation, exploration, and loop-closure in-tegration. For single-robot operation, GG RAPH updates graphs in milliseconds. At scale, it enables graph-based exploration policies to train across hundreds of parallel robots, reducing wall-clock training time by one order of magnitude. Across simulation and real-world experiments, these results establish GG RAPH as a unified graph infrastructure for both large-scale robot learning and deployment. 

Index Terms — Robot Navigation and Exploration, Graph-based RL, Software Tool for Robotics 

I. I NTRODUCTION 

Progress in mobile robotics has been driven by a small set of design tools that became shared infrastructure, including occupancy grids for planning [1], GPU elevation mapping for locomotion [2], OpenCV for perception [3], PyTorch for learning [4], and massively parallel simulators for RL [5]. Each is valuable because one implementation serves both deployment on a robot and training in simulation, so improvements on either side transfer. Graphs have long been used for robot planning. A navi-gation graph stores sparse collision-free nodes connected by traversable edges, and nodes can carry frontiers, traversabil-ity, semantics or learned scores. Such graphs underpin clas-sical exploration planners [6–8] and a line of learned policies that reason over the graph with Graph Neural Networks [9– 11]. Despite this, no shared tool builds and maintains these graphs. Deployment planners construct them inside planner-specific, single-robot code. Learning pipelines rebuild them for every environment on the CPU, so a 16-worker training run spends much of its wall-clock time maintaining graphs rather than learning. To address this gap, we present GG RAPH , a GPU-resident navigation-graph library that serves as one design tool for both deployment and learning (Fig. 1). GG RAPH takes occu-pancy grids or elevation maps as input. It samples collision-free waypoints, merges them incrementally into a persistent world-frame graph with stable node identities, and attaches per-node attributes through a layer system. Shortest paths, connectivity and frontiers are all available as CUDA tensors. The same implementation serves single-robot deployment through ROS 2 and policy learning across many parallel environments. Building such a library raises some technical challenges. First, the graph changes at every step, as each observation adds a varying number of nodes and edges that must be merged into a graph already covering the explored world. Second, existing graph builders rely on sequential data structures, such as priority queues and per-node objects, that cannot run in parallel on a GPU. Third, learning re-quires hundreds of such graphs, each growing at a different rate, to be updated together. Fourth, on a real robot the graph must survive loop closure, which moves every node placed since the drift began. GG RAPH stores each graph as parallel tensors with stable node identities, so adding, merging, pruning and correcting nodes are single vectorized operations. It merges each observation with one batched nearest-neighbor assignment and one line-of-sight kernel over all candidate edges. It also reformulates graph search as edge-parallel Bellman–Ford and pointer-jumping connected arXiv:2610.28953v1 [cs.RO] 20 Oct 2026 components, running one robot or N environments through the same kernels. The novel contribution of GG RAPH is to make the navigation graph itself a batched, GPU-resident, loop-closure-aware data structure shared by deployment and learning. To our knowledge, no other library provides this capability. Our contributions are: 1) An open-source GPU navigation-graph library. An extensible layer system stores geometric, semantic and learned attributes per node, and ROS 2 and batched interfaces let the same code serve deployment and learning (Sec. IV-A). 2) Validation in robot deployment and policy learning. 

We use GG RAPH to build 3-D graphs from real-world sensor data, attach frontier and semantic layers, and correct the whole graph after loop closure in one vectorized pass. Used as a batched RL environment, GG RAPH trains graph-based exploration policies that reach the quality of prior learned policies in a frac-tion of the training time and outperform baselines on held-out maps, on a ground vehicle in a high-fidelity simulator, and on a real robot (Secs. V-A and V-B). 3) Scalability benchmarks. Graph updates take just tens of milliseconds as graphs grow to a million nodes, and environment-step throughput scales with the number of parallel robots, reaching 27 × that of a SoTA baseline (Secs. V-A.3 and V-B.1). II. R ELATED WORK 

We review representations for navigation, graph software libraries, and learning-based exploration, identifying in each the gap that GG RAPH addresses. 

A. Representations for Navigation 

Early navigation in unknown environments used 2-D oc-cupancy grids [1], with frontier-based exploration driving the robot toward free cells that border unexplored space [14]. Volumetric maps such as OctoMap [15] and Voxblox [16] store occupancy or distance to surfaces across a 3-D volume. Topological maps [17–19] keep only the places a robot can reach and the transitions between them, and scene graphs [20] organize places into a semantic hierarchy. Exploration planners combine both. GBPlanner [7] plans over local and global graphs built on a volumetric map, and TARE [6] keeps a sparse roadmap along the past trajectory with dense point-cloud data around the robot. In both, the graph sits on a dense map that the planner still queries to score exploration gain. GG RAPH instead makes the graph the primary representation, storing frontier, semantic and learned attributes on its nodes and using dense maps only as transient inputs, so one graph serves both classical planners and learned policies. 

B. Graph Libraries and Ecosystems 

Navigation planners mutate their graphs as the robot explores, merging local observations into a global graph in custom C++ or Python code inside each planner [6, 7, 9].

Graph learning frame-works such as PyTorch Geometric [12] are fully tensorized and batch graphs by stacking adjacency matrices block-diagonally, but treat each graph as a fixed model input without spatial merging, and graph analytics libraries such as cuGraph [13] run GPU analytics over graphs built from edge lists. GG RAPH combines GPU acceleration, spatial merging, navigation and exploration operations, and batched policy learning in one library. 

C. Learning-Based Robot Exploration 

Learning-based exploration trains reinforcement learning policies to choose where a robot goes next, and graphs suit them because one graph is both the map the robot traverses and the input a graph neural network [23] reasons over. Chen et al. [24] trained graph neural network policies with DQN and A2C over a graph of past poses, landmarks and candidate frontiers for exploration under localization uncertainty. ARiADNE [9] connects uniformly distributed viewpoints into a collision-free graph and trains an attention network with soft actor-critic to pick the next neighboring viewpoint, using each node’s count of observable frontiers as a feature. Its large-scale successor [10] adds graph rarefaction and a privileged critic, and GRATE [11] uses a graph transformer encoder and Kalman-filtered waypoints. These three train in 2-D grid worlds with 16 to 32 Ray workers for one to three days, and in ARiADNE’s released code each worker builds its graph in Python on the CPU. GG RAPH 

builds and merges every environment’s graph on the GPU, so hundreds of environments step as one tensor operation, which makes on-policy methods such as PPO [25] practical, as in massively parallel locomotion learning [26]. III. P ROBLEM FORMULATION

.IV. M ETHODOLOGY 

Our approach has two components. A batched graph builder (Sec. IV-A) maintains the navigation graph. GG RAPH implements the update f of Sec. III as a GPU pipeline that samples a local graph from each observation Ot,merges it into the persistent world-frame graph Gt, and writes the per-node scores St, running one robot or N environments through the same kernels. A parallel reinforcement-learning pipeline (Sec. IV-B) then solves the MDP of Sec. III. We parameterize the policy π as a Graph Neural Network (GNN) that acts directly on Gt and train it across hundreds of GG RAPH environments stepped together on the GPU. 

A. Batched Graph Builder 

Local graph construction. A frontier kernel scans the input map once, emitting the free-space mask and the frontier set in a single pass. The waypoint sampler then populates the mask with well-spaced nodes through three complementary passes. A skeleton pass places nodes along the medial axis of free space, a boundary pass places nodes along inflated obstacle contours to cover corridors and walls, and a free-space pass uses a GPU distance transform to fill open regions until every free cell lies within a fixed radius of some node. This is a tensorized implementation of the graph builder logic in NVIDIA’s SWAGGER library [21]. For learning experiments that require the uniform lattice of prior work [9], a world-anchored lattice can replace the three passes without changing anything downstream. For 2.5-D elevation inputs, a slope and step-height stage lifts the map into a 3-D traversability volume before sampling, which is what produces the graphs over ramps and stairs.

Candidate edges are proposed by a radius query and validated with GPU-parallel line-of-sight checks against the obstacle memory, with surviving edges added subject to a per-node degree cap and a periodic pruning of redundant edges. Node and edge arrays are parallel tensors, so every mutation is a vectorized gather or scatter, and a retention rule prunes long-unobserved nodes to bound graph size. Multi-layer attribute system. Per-node attributes are exposed through registered graph layers . A compute layer 

executes a user kernel against the current graph each frame (the built-in frontier layer of Fig. 3A is one), while an 

external layer ingests asynchronous scores from outside the library and persists them across frames (the terrain-semantics layer of Fig. 3B). Merge policies (overwrite, blend, moving average) govern how repeated observations combine. Every layer is a GPU tensor aligned with the node array, so its output is consumed without copies, as a feature matrix for a policy or a scalar score for a planner. 

GPU graph search. For planning, the global graph is materialized in compressed-sparse-row form directly from the edge tensors. GG RAPH provides parallel breadth-first search, a Bellman–Ford kernel for single- and multi-source shortest paths, and pointer-jumping connected components. Bellman–Ford is preferred over Dijkstra because it relaxes all edges in one kernel launch, whereas a priority queue serializes. 

Loop closure. Each node stores the index of the odometry frame at which it was created. When an external SLAM module supplies a corrected trajectory, graph correction reduces to a single O(N ) vectorised gather that translates each node by the displacement of its parent frame, with no graph traversal, no sensor re-integration, and no occupancy reprojection. A subsequent GPU node remerge collapses spatially coincident nodes from overlapping traversals, and a frontier validity recheck demotes boundary nodes that the correction has rendered interior to the graph’s free nodes. 

Batched execution. For policy training, N independent builders share the same kernels and are stepped together each simulator tick, producing padded position, adjacency, frontier, and attribute tensors that a graph-conditioned policy consumes directly. Because per-environment graph state is itself GPU-resident, only kernel saturation, not Python or PCIe overhead, bounds the batch size (Sec. V-B.1). 

ROS 2 deployment. A ROS 2 wrapper accumulates a sensor stream and odometry into a rolling map, feeds it to the incremental builder, and exposes the layer system so external modules publish per-position scores. The exploration node of Sec. V-B.3 is one such wrapper. 

B. Parallel Policy Learning For Exploration 

In order to utilize GG RAPH ’s batched graph builder, we train our GNN exploration policy using SAC or PPO [25], following the massively parallel training setup of [26]. Unlike previous work where SAC was used [9–11], GG RAPH un-locks the use of on-policy PPO and large-scale parallelization by providing high-throughput environment data. GG RAPH 

maintains a navigation graph for each of N environments. We use separate actor and critic networks, each shared across all environments. The entire training loop runs on the GPU, including graph maintenance, environment updates, observa-tion and reward computation. Keeping the environment and learner on the GPU avoids CPU–GPU transfers. 

Exploration environment: We train exploration policies in 2-D grid worlds represented as occupancy maps. Each map specifies free and occupied cells, while the robot maintains a belief map that additionally marks unobserved cells as unknown. Simulated sensor observations update this belief as the robot moves, and GG RAPH maintains a navigation graph from the observed free space. We use the same training maps as ARiADNE [9], obtained from its public repository. Since ARiADNE does not release its validation split, we generate 150 new maps using the dungeon generator of [27]. These new validation maps are excluded from training and grouped into easy, medium, and complex tiers of 50 maps each, with difficulty increasing through the number of dead-end corridors and the free-space boundary-to-area ratio. 

Reward: We use the exploration reward of prior work [9– 11], which rewards exploration progress and penalizes travel distance. A frontier cell is an unknown cell adjacent to known free space. At each step, the robot receives reward rt =

a · rf − b · rd + rc, where rf = F (Gt−1, Gt) counts the frontier cells removed during the step and rd = ∥xt −xt−1∥2

is the distance traveled. We use the same coefficients as [9], 

a = 1 /64 and b = 1 /50 , with a completion bonus of rc = 20 

when exploration is completed and rc = 0 otherwise.

2) Loop Closure: We evaluate on a closed square tra-jectory under a combined drift of 22 % scale error and 160 mm/m additive world-frame bias, producing a pre-correction loop-closure gap of 14.08 m (Fig. 4A). The full correction pipeline restores the closed loop (Fig. 4B) in 2.26 ms. Such efficiency is not feasible for volumetric repre-sentations. An occupancy grid or TSDF over the same envi-ronment requires an O(W ×H) pixel-level warp followed by re-ray-casting or signed-distance fusion. In GG RAPH , each node carries the index of the odometry step that placed it, so loop closure reduces to a single vectorised pass. 

3) Graph Update Time: A deployed planner updates its graph every cycle, so the cost of that update bounds how large a world a single robot can map in real time. Fig. 5 measures GG RAPH update time as the global graph grows. A full update takes about 7 ms at 100 ,000 nodes. Compared to a SoTA baseline implementation using SWAGGER and NetworkX, this is about 120 × faster. The update time is just 62 ms at a million nodes. At a 0.5 m node sampling distance, a million nodes can cover a 500 ×500 m area. Building the local graph, selecting candidate edges and checking collisions take about 3 ms at every size, and the growth comes from merging nodes, de-duplicating edges and pruning node degrees. 

B. Robot Learning 

Autonomous exploration underpins search and rescue and inspection, and graph-based planners have been fielded in settings like the DARPA Subterranean Challenge [6, 7]. Learned policies over the same graphs now report the shortest paths on common benchmarks [9–11], but their training infrastructure has not kept pace. Massively parallel GPU sim-ulation cut locomotion training from days to minutes [26], while graph-based exploration still rebuilds its environment on the CPU. Thus, GG RAPH ’s robot learning experiments are aimed at showing how the library serves as a foundation for accelerating modern exploration policy training. We build on prior work on attention-based graph exploration policies [9– 11] where robots explore 2-D grid worlds while maintaining graphs in Python. In these methods, experience is collected in parallel using Ray [29] at one worker per environment, capping parallelism at CPU thread count. We replicate their experiments using GG RAPH to maintain the navigation graph for each robot, then measure the resulting gains in through-put, training time and final policy performance. 

1) Batched Environment-Step Throughput: We compare environment-step throughput between GG RAPH and ARi-ADNE’s CPU-based graph manager as the number of parallel robots grows. A step applies the selected action, updates the graph, and returns the next observation and reward. 

Setup: Both pipelines run ARiADNE’s released check-point on 200 maps drawn at random from the training set of Sec. IV-B, with identical graph-sampling parameters so each measurement spans the same distribution of graph sizes. The measured interval begins at the end of policy inference and closes once the next observation, reward and termination flags are available. For N parallel robots we accumulate wall-clock time Tenv over H = 128 steps per robot and report throughput Renv = N H/T env in environment steps per second. GG RAPH batches updates across N environments on the GPU while ARiADNE distributes them over 16 Ray workers. We sweep N from 1 to 1024 on an AMD Ryzen 7 8700F with an RTX 5070 Ti. 

Results: Fig. 6A shows that the throughput advantage of GG RAPH grows with the number of parallel robots, from approximately 6 × at N = 16 to 26 × at N = 256 . Its throughput then levels off, reaching about 6,500 env-steps per second at N = 512 , compared with 244 for ARiADNE, a 27 × speedup.

3) Deployment of the Learned Policy in a High-Fidelity Simulator and the Real World: We deploy the learned poli-cies on a simulated ground vehicle in the CMU autonomous exploration development environment [30]. It provides a Gazebo model of a skid-steer vehicle with a Velodyne VLP-16 LiDAR, a state estimator, terrain analysis, and a local planner that tracks a waypoint at up to 2 m/s. An OctoMap belief built from the vehicle’s registered scans is projected to a 2-D occupancy grid, a navigation graph is maintained on it, and at each step the policy selects the next goal node, which becomes the vehicle’s waypoint. Each policy acts on the graph geometry it was trained on (4 m node spacing, 16 m sensor range, 12.8 m utility range); ours uses the graph built by GG RAPH , and the ARiADNE policies use their own builder. We compare paths at equal coverage. The 150 ×150 m world is divided into 1 m cells, and a cell counts as covered once the vehicle has passed within 20 m of it. Coverage is the fraction of cells covered, and runs are cut at the moment their coverage first reaches 99.8 %. Fig. 9 shows one run of each planner in a large-scale outdoor map. ARiADNE’s recipe trained with its own code for 2 h takes the longest path to explore, 1469 m in 801 s; much of that distance comes at the end of the run, when the vehicle is forced to cross its previous path again to reach the last unexplored regions. TARE follows at 1229 m in 668 s. ARiADNE’s released checkpoint, reported to need about 24 h of training, and our SAC policy, trained for 2 h with 512 robots on GG RAPH , yield comparable performance. They drive 1143 m in 642 s and 1139 m in 615 s, respectively. Our PPO policy, trained for 1.5 h with 512 robots on GG RAPH ,drives the shortest path, 1040 m in 655 s, 9 % shorter than the released checkpoint. Finally, we deploy the same PPO policy on the Spot robot exploring an office floor (Fig. 11). The policy was trained entirely on 2-D grid-world maps and has never seen real data, yet it transfers directly, because its observation is the graph and not the raw sensor feed. The robot’s path length was 157 m. In certain areas, the cameras saw through glass doors and free space was mapped inside closed rooms and nodes were sampled there. The policy initially targeted these nodes for their frontier utility, but once the local planner could not reach them, the graph builder’s connectivity check dropped them from the robot’s graph component and the policy moved on to the reachable frontiers. VI. C ONCLUSION 

We presented GG RAPH : an open-source, GPU-resident navigation-graph library that serves as one design tool for robot deployment, navigation and policy learning. It main-tains frontier detection, node sampling, incremental merging, edge validation and attribute layers on the GPU. The same GPU kernels build a 3-D graph, host frontier and semantic layers that classical planners read directly, correct a drifted graph after loop closure in milliseconds, and step a thousand simulated robots per tick. Using GG RAPH , training RL-based exploration policies reaches the quality of the baseline graph-Fig. 11: The simulation-trained PPO policy successfully explores a real indoor map on the Spot robot using on-board cameras only. The top-down point cloud (colour = height) with the 157 m trajectory is shown. Insets: an image of the corridor and the robot. 

based policies in an order of magnitude less wall-clock time. The policy outperforms classical planners on held-out maps, TARE in simulation, and SoTA methods like ARiADNE and GRATE at similar training budgets. It also transfers to a ground vehicle in a high-fidelity simulator and in the real world. Future work will replace the per-platform tuning of sampling parameters with learned sampling of the nodes in the graph and handle dynamic obstacles. As node attributes are tensors, the same batched environment can potentially extend to image-conditioned policies, with a vision encoder writing per-node embeddings from an RGB feed like our semantic layer already does (Fig. 3B).
